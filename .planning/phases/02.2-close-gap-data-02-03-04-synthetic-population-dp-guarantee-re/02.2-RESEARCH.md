## Summary

Phase 02.2 closes three data gaps left from Phase 1: the 50K synthetic population was never generated (CASD access pending), the ε ≤ 1.0 DP proof was never executed, and the shock matrix is a 2.6KB placeholder — not calibrated to real Mésange coefficients. The infrastructure code exists and is well-structured; the gap is **execution** — producing actual artifacts from publicly available data sources while CASD access is pending.

The three sub-pipelines compose into a single re-runnable `generate_dist.py` orchestration that produces: `population-v2025.1.json` (50K profiles + .meta.json DP sidecar), `shockmatrix-v2025.1.parquet` (calibrated 3D grid), and the TypeScript `PopulationCache` class that mirrors the battle-tested `ScenarioCache` pattern.

**Primary recommendation:** Execute the three pipelines independently first (unblocked by each other), then converge into the unified `generate_dist.py` orchestration. The TypeScript `PopulationCache` follows the exact same architecture as `ScenarioCache` — separate module, zero changes to existing code.

- **D-01:** Use INSEE aggregate tables (Enquête Revenus Fiscaux et Sociaux, Recensement) as the data source for synthetic population generation. Re-runnable pipeline — when CASD microdata access is approved, swap the data source and regenerate.

- **D-10:** DP noise applied to aggregates only (population-level statistics in .meta.json). Individual 50K profiles remain unmodified for accurate O(1) micro lookups. Phase 3/4 UI queries aggregate stats for distributional charts — noise there prevents reconstruction.

### Pattern 1: PopulationCache Mirrors ScenarioCache

**What:** `PopulationCache` follows the exact same O(1) HashMap architecture as `ScenarioCache`. No WASM, no network calls — pure TypeScript data structure loaded via `postMessage` from the orchestrator.

**When to use:** Any data lookup that needs <1ms response time and can be serialized as JSON. The orchestrator fetches on the main thread, then transfers parsed objects to the worker.

**Example:**
```typescript
// Source: mirrors existing ScenarioCache pattern in scenario-cache.ts
// webapp/src/engine/population-cache.ts

import type { Profile } from './types';

export interface PopulationDoc {
  version: string;
  reference_year: number;
  profiles: Profile[];
  meta: {
    dp_epsilon: number;
    dp_data_source: string;
    dp_proof_timestamp: string;
    sha256: string;
  };
}

export class PopulationCache {
  private profiles = new Map<string, Profile>();
  private byDecile = new Map<number, Profile[]>();
  private byAgeGroup = new Map<string, Profile[]>();
  private meta: PopulationDoc['meta'] | null = null;

  getProfile(id: string): Profile | undefined {
    return this.profiles.get(id);
  }

  getProfilesByDecile(decile: number): Profile[] {
    return this.byDecile.get(decile) ?? [];
  }

  getProfilesByAgeGroup(label: string): Profile[] {
    return this.byAgeGroup.get(label) ?? [];
  }

  getMeta(): PopulationDoc['meta'] | null {
    return this.meta;
  }

  getProfileCount(): number {
    return this.profiles.size;
  }

  static fromDoc(doc: PopulationDoc): PopulationCache {
    const cache = new PopulationCache();
    cache.meta = doc.meta;

    for (const profile of doc.profiles) {
      cache.profiles.set(profile.profile_id, profile);

      // Pre-index by decile (if revenu_fiscal available)
      if (profile.revenu_fiscal !== undefined) {
        const decile = Math.floor(profile.revenu_fiscal / 10000) % 10; // simplified
        if (!cache.byDecile.has(decile)) {
          cache.byDecile.set(decile, []);
        }
        cache.byDecile.get(decile)!.push(profile);
      }

      // Pre-index by age group
      if (profile.age !== undefined) {
        const ageGroup =
          profile.age < 35 ? 'jeune' :
          profile.age < 50 ? 'actif' :
          profile.age < 65 ? 'senior' : 'retraite';
        if (!cache.byAgeGroup.has(ageGroup)) {
          cache.byAgeGroup.set(ageGroup, []);
        }
        cache.byAgeGroup.get(ageGroup)!.push(profile);
      }
    }

    return cache;
  }
}
```

### Pattern 3: Hybrid IRF + Elasticity Shock Matrix Calibration

**What:** Combine published Mésange impulse response functions (dynamic shape over 5 years) with OLS-estimated budget elasticities from historical execution data (scaling magnitude). The IRFs define the propagation skeleton; the elasticities scale it to French fiscal reality.

**Pseudo-algorithm:**
```python
# Source: D-05, D-06, D-07 decisions
def calibrate_shock_matrix():
    # 1. Load published IRFs (shape, not magnitude)
    irfs = load_published_irfs()  # dict: output_var → array[horizon_years]

    # 2. Estimate elasticities from budget execution data (2000-2024)
    elasticities = estimate_budget_elasticities()  # OLS regression

    # 3. For each grid point (tax_rate_i, spend_level_j, horizon_k):
    for tax_rate in tax_breakpoints:    # 12 points in [0.5, 2.0]
        for spend_level in spend_breakpoints:  # 12 points in [0.7, 1.5]
            for horizon in horizon_breakpoints:  # 12 points [1, 5]
                # Scale IRF by tax elasticity and spend multiplier
                tax_shock = (tax_rate - 1.0) * elasticities['tax_gdp']
                spend_shock = (spend_level - 1.0) * elasticities['spend_gdp']
                grid[tax_idx, spend_idx, horizon_idx, :] = (
                    irfs * (1 + tax_shock + spend_shock)
                )
    # 4. Export as Parquet/Zstd
    export_parquet.export_shock_matrix(grid, breakpoints, convex_hull, path)
```

**Output variables (4):** gdp_growth, employment_change, deficit_change, debt_to_gdp_ratio

### Anti-Patterns to Avoid

- **Hand-rolling Laplace noise in NumPy:** `dp_inject.py` explicitly forbids `numpy.random.laplace()` — always use OpenDP's `.map(d_in=1)` for formal proof. Directly in module rule comment.
- **Extrapolating outside convex hull:** `macro-interpolate.ts` already gates with `isInsideHull()` before interpolation. The calibrated matrix must produce valid hull equations. Never allow silent extrapolation (PITFALLS.md Pitfall 2).
- **Applying DP noise to individual profiles:** D-10 explicitly states noise goes on aggregates only. Individual profiles are exported unmodified for accurate micro lookups. `.meta.json` carries the DP proof.
- **Using YAML at runtime:** `export.py` already produces JSON. Keep JSON format — do not introduce YAML parsing to the TypeScript runtime.
- **Mixing SDV 1.x and 2.x APIs:** The pipeline code (`train.py`, `preprocess.py`) uses SDV 1.36.1 API (`SingleTableMetadata`, `CopulaGANSynthesizer`). SDV 2.x may have different API. Stay on 1.36.1 until CASD data migration.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Laplace noise for DP | `np.random.laplace()` | OpenDP `dp.m.make_laplace(scale=...)` with `.map(d_in=1)` | Only OpenDP provides formal, auditable ε proof. Hand-rolled noise has no privacy guarantee. |
| Convex hull computation | Gift-wrapping algorithm | `scipy.spatial.ConvexHull` (Qhull) | Qhull handles degenerate cases (collinear points), provides volume/bounds verification. Decades of scientific validation. |
| Copula-based dependency modeling | Manual Gaussian copula in NumPy | SDV `CopulaGANSynthesizer` | Handles categorical encoding, numerical distributions (beta/gamma), min/max enforcement, and multi-variable covariance. |
| Gzip compression for population JSON | Custom compression wrapper | Python `gzip` stdlib (pipeline) + browser `Content-Encoding: gzip` (serve) | Standard, universally supported, sufficient for 50-150KB target. |
| Trilinear interpolation | Custom weighted average | `macro-interpolate.ts` (existing, tested) | 12 tests passing, convex hull gating, zero WASM dependencies. Don't rebuild. |

**Key insight:** The most dangerous hand-roll in this domain is DP noise. OpenDP's `.map(d_in=1)` is the only way to get a **formal** ε proof — NumPy Laplace is computationally equivalent but has no audit trail. The CNIL requires auditable privacy guarantees, not just correct math.

## Common Pitfalls

### Pitfall 1: SDV / Python Version Incompatibility

**What goes wrong:** SDV 1.36.1 fails to install with `ResolutionImpossible` error on Python 3.13.13. The pip dry-run shows a dependency conflict. CopulaGAN training cannot proceed without a working SDV environment.

**Why it happens:** SDV 1.x has specific Python version constraints (typically ≤3.11 or ≤3.12). Python 3.13 introduced breaking changes to some C extensions that SDV's dependency tree (torch, rdt, sdmetrics) has not yet adopted.

**How to avoid:** Either (a) downgrade the venv Python to 3.11 or 3.12, (b) use SDV 2.x if it supports Python 3.13, or (c) use Docker with a pinned Python 3.11/3.12 image for the pipeline. The pyproject.toml already specifies `requires-python = ">=3.10"` which is flexible.

**Warning signs:** `pip install sdv==1.36.1` fails with `ERROR: ResolutionImpossible` on Python 3.13.

**Verification:** Attempted `pip install sdv==1.36.1 --dry-run` in the existing Python 3.13.13 venv — failed with ResolutionImpossible. This is a **blocking issue** for the synthetic population pipeline.

### Pitfall 2: DP Budget Exhaustion (PITFALLS.md Pitfall 3)

**What goes wrong:** The ε ≤ 1.0 guarantee is declared but the budget is consumed by per-query dashboard operations, rendering the guarantee meaningless.

**Why it happens:** Our architecture already mitigates this — D-10 states DP noise is applied to aggregates only, at generation time. Dashboard queries pre-noised aggregates, not raw profiles. The `dp_inject.py` module explicitly budgets ε/5 per decile, ε/3 per age bracket, ε/2 for Gini, and the budget is consumed **once** during pipeline execution.

**How to avoid:** Already handled by architecture. Verify that `inject_dp_privacy()` is called exactly once per population generation and that the `.meta.json` `total_epsilon_consumed` never exceeds 1.0. No runtime DP queries.

**Warning signs:** `total_epsilon_consumed > epsilon_budget` in dp_report. Missing `dp_proof_timestamp` in .meta.json.

### Pitfall 3: Curse of Dimensionality (PITFALLS.md Pitfall 9)

**What goes wrong:** The 3D grid (tax × spend × horizon) with 12 breakpoints per dimension = 1,728 grid points × 4 output variables = 6,912 Float32 values ≈ 27KB uncompressed. This is well within limits. But if someone adds more dimensions (e.g., separate IR/IS/TVA sliders), the grid explodes to 12⁵ = 248,832 points.

**Why it happens:** D-06 specifies exactly 3 dimensions: tax_rate, spend_level, time_horizon. The existing `grid_build.py` enforces MAX_DIMENSIONS=4 (D-08). This is safe for v1.

**How to avoid:** Stay with 3 dimensions. The `macro-interpolate.ts` engine and `ShockMatrixData` interface are hardcoded for 3D (tax, spend, horizon). Adding dimensions would require engine changes. Document that the 3D limit is architectural.

**Warning signs:** Grid size > 5MB compressed. `build_cartesian_grid()` assertion failure on >4 dims.

### Pitfall 4: Shock Matrix Grid Convention Mismatch

**What goes wrong:** The calibrated shock matrix is exported from Python with different dimension ordering than `macro-interpolate.ts` expects, causing silent wrong interpolations.

**Why it happens:** `macro-interpolate.ts` uses row-major (C-order) indexing: `((taxIdx * nSpend + spendIdx) * nHorizon + horizonIdx) * NUM_FEATURES`. If the Python `export_parquet.py` or the grid construction uses a different convention, the browser engine will read wrong values.

**How to avoid:** D-13 explicitly states: preserve existing 3D grid convention and dimension-major obs ordering. The `export_parquet.py` flatten logic produces rows with tax_rate, spending_level, horizon_year in that order. The `macro-interpolate.ts` `parseMatrixBytes()` reads taxBp, spendBp, horizonBp in that order. Verify with integration test that interpolates at known grid points and checks exact values.

**Warning signs:** Integration test that interpolates at grid-center returns wrong values. Parquet column order differs from expected tax → spend → horizon.

## Open Questions

1. **SDV Python version resolution**
   - What we know: SDV 1.36.1 fails pip install on Python 3.13.13 with ResolutionImpossible
   - What's unclear: Whether SDV 1.36.1 works on Python 3.11 or 3.12 (most likely yes — these were standard when 1.36.1 was released)
   - Recommendation: Create a new venv with Python 3.11 or 3.12 for the pipeline. If neither works, evaluate SDV 2.x API compatibility with existing `train.py` and `preprocess.py` code (which uses `SingleTableMetadata`, `CopulaGANSynthesizer` from SDV 1.x API)

2. **Specific INSEE table URLs / identifiers**
   - What we know: D-01 names ERFS, Recensement, Enquête Patrimoine as sources
   - What's unclear: Exact URLs, file formats (CSV vs Excel vs SDMX), column mappings to the 10-field schema
   - Recommendation: The planner should include a research task to locate the specific INSEE data files on insee.fr before implementing the loader. Consider using the insee.fr API if direct file download is unavailable

3. **Which DG Trésor working papers contain usable IRFs**
   - What we know: D-05 specifies published IRFs from DG Trésor/Mésange working papers
   - What's unclear: Which specific working papers (e.g., "Document de Travail n°2023/XX"), which variables are published (GDP, employment, deficit, debt), at what horizon granularity
   - Recommendation: Planner should include a discovery task. If no published IRFs are found with sufficient detail, fall back to economic theory sign patterns + published budget elasticities, documented transparently

4. **PopulationCache TypeScript Profile type definition**
   - What we know: The schema `synthetic_profile.schema.json` defines 10 fields (with 6 required). The TypeScript `Profile` type must match.
   - What's unclear: Whether the Profile type in `types.ts` should include optional fields (enfants_a_charge, loyer_mensuel, statut_occupation) from the schema and whether `revenu_fiscal` needs the decile pre-computation at load time
   - Recommendation: Define a `Profile` interface that exactly matches the JSON schema. Add pre-computed `decile` as a derived field (not stored in JSON, computed at cache construction time)

5. **Shock matrix breakpoint ranges (± bounds) for tax_rate and spend_level**
   - What we know: D-06 specifies 12 breakpoints. D-09 from Phase 1 specifies tax [0.5, 2.0], spend [0.7, 1.5]. `grid_build.py` defaults match these.
   - What's unclear: Whether these ranges are sufficient for the political scenarios (e.g., extreme tax cuts or spending increases may go beyond [0.5, 2.0])
   - Recommendation: Start with the Phase 1 defaults (tax [0.5, 2.0], spend [0.7, 1.5], horizon [1, 5]). If political scenarios require wider ranges, expand bounds but stay within convex hull coverage of the grid
