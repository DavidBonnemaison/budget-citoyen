<objective>
Implement the PopulationCache TypeScript class — an O(1) HashMap lookup structure that mirrors the battle-tested ScenarioCache architecture. PopulationCache takes a PopulationDoc (array of Profile objects + metadata), indexes them by profile_id, pre-computes decile and age-group buckets for fast accessor queries, and exposes getProfile(), getProfilesByDecile(), getProfilesByAgeGroup(), getProfileCount(), and getMeta() methods. All lookups are O(1) average case. This is the runtime component that Phase 3 UI queries for household profile display and Phase 4 distributional analysis.

Purpose: Provide the TypeScript engine with typed, O(1) access to the 50K synthetic profiles stored in population-v2025.1.json. Without this cache, every profile query would require linear search or repeated JSON parsing.

Output: Working `population-cache.ts` module with `PopulationCache` class and `PopulationDoc` export, 14 passing vitest tests replacing Wave 0 stub.
</objective>

    File: webapp/src/engine/population-cache.ts (NEW)

    Mirror the ScenarioCache class structure exactly — same Map patterns, same static factory method naming, same mutability guards.

    ```typescript
    import type { Profile, PopulationDoc } from './types';
    ```

    The PopulationCache class:

    **Private fields:**
    - `profiles: Map<string, Profile>` — O(1) lookup by profile_id
    - `byDecile: Map<number, Profile[]>` — pre-indexed by revenu_fiscal decile (1-10)
    - `byAgeGroup: Map<string, Profile[]>` — pre-indexed by age bracket label
    - `meta: PopulationDoc['meta'] | null` — metadata from PopulationDoc
    - `profileCount: number` — cached count for O(1) getProfileCount()

    **Constructor:** private — all instances created via `fromDoc()`.

    **Decile computation:** At construction time, for each profile with `revenu_fiscal` defined:
    - Sort all profiles by revenu_fiscal
    - Compute decile boundaries as percentiles [10, 20, ..., 100]
    - Assign each profile to decile 1-10 based on its revenu_fiscal position
    - For efficiency: compute boundaries in a single pass, then assign each profile with binary search

    **Age group assignment:**
    - age < 35 → 'jeune'
    - 35 ≤ age < 50 → 'actif'  
    - 50 ≤ age < 65 → 'senior'
    - age ≥ 65 → 'retraite'
    - Missing age → skip (not added to any age group)

    **Public methods:**

    `getProfile(id: string): Profile | undefined` — Map.get() on profiles

    `getProfilesByDecile(decile: number): Profile[]` — Returns a COPY of the stored array (spread: `[...arr]`). Returns empty array for invalid decile (< 1 or > 10).

    `getProfilesByAgeGroup(label: string): Profile[]` — Returns a COPY of the stored array. Returns empty array for invalid label.

    `getProfileCount(): number` — Returns profileCount.

    `getMeta(): PopulationDoc['meta'] | null` — Returns meta.

    `static fromDoc(doc: PopulationDoc): PopulationCache`:
    1. Create new PopulationCache instance
    2. Set meta = doc.meta
    3. Iterate over doc.profiles:
       a. Set cache.profiles.set(profile.profile_id, profile)
       b. If profile.revenu_fiscal exists, collect for decile indexing
       c. If profile.age exists, assign to age group bucket
    4. After full iteration, compute decile boundaries and assign profiles to decile buckets
    5. Set profileCount = doc.profiles.length
    6. Return cache

    `static async loadFromJSON(url: string): Promise<PopulationCache>` — Same pattern as ScenarioCache.loadFromJSON():
    - fetch(url), check response.ok
    - Parse JSON as PopulationDoc
    - Return PopulationCache.fromDoc(data)
    - This method is for main-thread use (orchestrator). Workers use fromDoc() with transferred data.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| population-v2025.1.json → PopulationCache.fromDoc() | Untrusted JSON crosses into typed TypeScript — must validate structure before constructing cache |
| WorkerOrchestrator postMessage → PopulationCache.fromDoc() | Serialized data across worker boundary — JSON.parse runs on the worker side per D-12 |
| Profile.revenu_fiscal → decile computation | Numeric value used for percentile computation — must handle edge cases (NaN, Infinity, negative) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02.2-15 | Tampering | population-v2025.1.json integrity | mitigate | SHA-256 hash in doc.meta is validated against the JSON content before constructing cache (validate in loadFromJSON). fromDoc() accepts pre-validated docs — the orchestrator is responsible for hash verification before passing to worker. |
| T-02.2-16 | Denial of Service | Malformed PopulationDoc with massive profiles array | mitigate | fromDoc() iterates over all profiles but uses O(n) memory only (Map entries). 50K profiles × ~200 bytes = ~10MB — well within browser memory limits. If profileCount > 100000, log a warning (but don't reject — data contract says 50K). |
| T-02.2-17 | Information Disclosure | getProfilesByDecile() exposing individual profiles | accept | This is the intended API — Phase 4 distributional analysis needs decile-level profile lists. The profiles are already loaded in the worker's memory. No network exposure per D-12. |
| T-02.2-18 | Information Disclosure | Decile boundaries leaking individual revenu_fiscal | accept | Decile boundaries are aggregate statistics — they are the threshold values between deciles, not individual revenu values. These will be DP-noised in Plan 06. |
</threat_model>
