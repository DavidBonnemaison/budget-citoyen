<objective>
Implement the scenario data cache — a lightweight Rust module that loads the pre-computed scenario lookup table and provides O(1) citizen-mode results. Per CONTEXT.md D-11, wasm-micro is a SKELETON ONLY (scenario data cache, no formula engine). This replaces the original TaxBenefitSystem plan: instead of dispatching ~200+ formula functions, we deserialize pre-computed JSON and do HashMap lookups.

Purpose: Citizens get instant pre-computed household impact results. No formulas run in the browser, no data leaves the browser, and the lookup is deterministic (same JSON → same result, bit-exact). The scenario data was validated against openfisca-france at CI time (Plan 02-04), so correctness is guaranteed without runtime computation.

Output: Working ScenarioCache with O(1) lookup, integration tests against the real scenario data, and validation that cached results match the Python CI output.
</objective>

```rust
use budget_citoyen_core::scenario_types::{ScenarioDoc, ScenarioDefinition};
use budget_citoyen_core::types::MicroResult;
use std::collections::HashMap;

pub struct ScenarioCache {
    doc: ScenarioDoc,
    // Fast lookup index: (scenario_id, profile_id) → &MicroResult
    // Built at init time for O(1) access
}

impl ScenarioCache {
    /// Load scenario data from JSON string (passed from main thread per D-12).
    /// Deserializes and validates the scenario document.
    /// Builds lookup indices for O(1) access.
    pub fn load_from_json(json: &str) -> Result<Self, String>;

    /// Get pre-computed MicroResult for a citizen: scenario + profile.
    /// O(1) HashMap lookup — no computation, no formula dispatch.
    /// Returns None if scenario_id or profile_id not found.
    pub fn get_result(&self, scenario_id: &str, profile_id: &str) -> Option<&MicroResult>;

    /// List all available scenario IDs and names (for UI dropdown).
    pub fn list_scenarios(&self) -> Vec<(&str, &str)>;  // (id, name)

    /// Get scenario parameter set (for displaying reform details in UI).
    pub fn get_scenario_params(&self, scenario_id: &str) -> Option<&serde_json::Value>;
}
```

**Key difference from original TaxBenefitSystem:**
- OLD: `compute_all_taxes(&self, profile_index: usize) -> MicroResult` — ran ~200+ formula functions
- NEW: `get_result(&self, scenario_id: &str, profile_id: &str) -> Option<&MicroResult>` — HashMap lookup
- OLD: `SimulationState` with `&[f64; 16]` slider input → formula recomputation
- NEW: Sliders drive MACRO engine only. Micro results are fixed per scenario — no recomputation needed

**Data loading (D-12, D-18):**
- Main thread fetches `scenarios-v2025.1.json` as a static asset
- Main thread posts the JSON string to the worker via `postMessage`
- Worker calls `ScenarioCache::load_from_json(json_str)` — zero network access from worker
- Scenario data is ~8-50 KB (gzipped to ~2-10 KB) — trivial to load

**Test strategy (TDD):**
- Tests use `include_str!` to embed the real scenario data at compile time (cargo test — no browser needed)
- Tests verify: deserialization, lookup correctness, error handling (unknown scenario/profile), field completeness

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Phase 1 dist/ scenarios-v2025.1.json → serde_json::from_str | Pre-computed scenario data deserialized from static file. Must validate version tag and structure before building lookup indices. |
| ScenarioCache::get_result → caller | Lookup returns a reference to internally stored MicroResult — caller must not mutate. Rust borrow checker enforces this. |
| Main thread → Worker (scenario JSON string) | Scenario data transferred as JSON string via postMessage per D-12. Worker validates before caching. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-34 | Tampering | Version tag spoofing in scenario JSON | mitigate | load_from_json() validates version field starts with "scenarios-v" and matches expected reference year. Returns Err on mismatch. Caller cannot bypass version gate. |
| T-02-35 | Tampering | Malformed scenario JSON with missing results fields | mitigate | serde_json deserialization with strict typing. ScenarioCache validates that scenarios array is non-empty and each scenario has results. Missing required MicroResult fields cause deserialization failure (serde with deny_unknown_fields). |
| T-02-36 | Information Disclosure | Error messages exposing internal cache state | mitigate | Error messages describe failure type only (e.g., "Version mismatch: expected scenarios-v, got {actual}", "No scenarios found in data"). Never expose internal HashMap contents, profile data, or full ScenarioDoc in errors. |
| T-02-37 | Tampering | Scenario data tampered after CI export | mitigate | Scenario data generated by CI pipeline (Plan 02-04). SHA-256 integrity hash verified at CI time. Bundle scenario data with Phase 3 webapp build — immutable at deploy time. |
| T-02-38 | Denial of Service | Extremely large scenario JSON consuming WASM memory | mitigate | Scenario data is bounded: 32 profiles × 3-5 scenarios × <1KB per result = <160 KB. ScenarioCache validates scenario count (max 20) and results per scenario (max 100) at load time. Rejects oversized data with Err. Cross-ref: CI pipeline guarantees bounded output. |
</threat_model>
