<objective>
Create the Web Worker infrastructure that loads WASM engines and handles message-based communication with the main thread, plus the CI pipeline that gates all engine correctness. Workers are the runtime shell that enforces the privacy guarantee (MICRO-04): they never touch the network, all data arrives via postMessage with Transferable ArrayBuffers (D-12). The message protocol uses typed request/response with correlation IDs (D-11) so the main thread can discard stale responses from rapid slider interactions.

Purpose: Without workers, WASM engines cannot run in the browser. Without CI, there is no automated proof that correctness is maintained across changes.

Output: 4 TypeScript worker files, 1 CI workflow file, and verified `wasm-pack build` output consumable by the workers.
</objective>

```typescript
// Shared request type
type WorkerRequest = {
  id: string;                   // crypto.randomUUID() — correlation ID (D-11)
  type: 'INIT' | 'SIMULATE' | 'INTERPOLATE';
  payload: unknown;
};

// Shared response type
type WorkerResponse<T = unknown> = {
  id: string;                   // Echo back the request ID
  type: 'READY' | 'MICRO_RESULT' | 'MACRO_RESULT' | 'ERROR';
  payload: T | null;
};

// Micro-specific payloads
type SimulatePayload = { params: number[]; profileIndex: number };
type InitPayload = { paramsJson: string; populationJson: string };

// Initialization sequence (D-12):
// 1. Main thread: fetch("parameters-v2025.1.json") + fetch("population-v2025.1.json")
// 2. Main thread: worker.postMessage({ id, type: 'INIT', payload: { paramsJson, populationJson } })
// 3. Worker: await init() → engine = MicroEngine.new(paramsJson, populationJson) → postMessage({ id, type: 'READY' })
// 4. Main thread: now ready for SIMULATE requests
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Main thread → Web Worker (postMessage) | Structured data transferred between JS contexts. Transferable ArrayBuffers used for zero-copy (D-12). |
| Web Worker → WASM memory | WASM linear memory is shared within the worker — no cross-worker access. |
| CI runner → crates.io / npm / PyPI | Dependency downloads during CI. Cargo.lock integrity enforced. |
| CI runner → GitHub Actions artifacts | WASM build output uploaded as artifacts for deployment. Must not contain secrets. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-17 | Information Disclosure | Worker postMessage payloads | mitigate | WorkerResponse payloads contain only computation results, never profile raw data. Profile data stays in WASM linear memory — never serialized into postMessage responses. |
| T-02-18 | Tampering | CI supply chain (wasm-pack download) | mitigate | Pin exact version: `cargo install wasm-pack --version 0.14.0`. Verify checksum via `cargo install --locked`. |
| T-02-19 | Denial of Service | Infinite loop in WASM (CI timeout) | mitigate | CI jobs have `timeout-minutes: 15`. cargo test limited to unit/integration (no long-running benchmarks). |
| T-02-20 | Information Disclosure | CI artifacts (WASM binaries) | accept | WASM binaries are public artifacts (browser downloads them). No secrets embedded. Debug symbols stripped via release profile. Risk accepted. |
| T-02-21 | Tampering | Web Worker import of WASM | mitigate | Workers import WASM via `init()` from wasm-pack pkg/ directory. Subresource Integrity (SRI) hashes verified at deployment time (Phase 3/5 responsibility). |
</threat_model>
