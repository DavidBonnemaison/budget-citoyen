## Summary

Deep review of the scenario pre-compute pipeline (Python → JSON), the TypeScript scenario cache consumer, and the CI workflow that validates both. The review traced call chains from `precompute.py` → `scenario_definitions.py` → `_compute_scenario_result` → subordinate computation functions, and cross-referenced against the TypeScript `ScenarioCache` consumer and schema validation.

**Critical finding:** The IR scale extraction logic in `_compute_scenario_result` (precompute.py:322-330) strips custom bracket thresholds/rates from ALL scenario overrides and replaces them with a flat linear multiplier on the hardcoded baseline brackets. This means:

- **LFI/NFP**: 14 custom brackets (0% → 90%) are discarded; IR is computed at ~9% of baseline (scale=0.01/0.11) — dramatically **lower** than intended for high incomes.
- **PS**: 8 custom brackets (0% → 60%) are discarded; IR is **identical to baseline** (scale=0.11/0.11=1.0) — 28 of 32 profiles produce identical results.
- **Renaissance**: 4-bracket simplification discarded; IR identical to baseline.
- **LR, RN**: Brackets at incorrect thresholds; only a flat scale applied.

All 14 generated scenarios in `scenarios-v2025.1.json` contain incorrect IR values for any scenario with custom brackets. The expansion-2025 scenario accidentally produces correct results because its brackets are exactly 90% of baseline on all tiers.

Additionally, a false-positive test makes the pipeline appear validated when it never actually runs: `test_scenario_precompute.py:137` reads key `"profils"`/`"profiles"` but the actual JSON key is `"test_fixtures"`, returning an empty list that causes the test to silently pass with zero assertions against fixture data.

## Critical Issues

### CR-01: IR bracket overrides are silently ignored — all custom brackets discarded in favor of flat scale factor

**File:** `packages/data-pipeline/src/scenarios/precompute.py:322-330`
**Issue:** When `impot_revenu.bareme` is present in a scenario's `parameterOverrides`, the function only extracts the ratio of the first non-zero bracket rate to the baseline 0.11 as a flat scale factor. The actual bracket thresholds, all bracket rates beyond the second, and the number of brackets are silently discarded. `_compute_ir_bareme` always uses its own hardcoded 5-tier brackets (lines 134-139) multiplied by this scale.

**Evidence:**
- PS-2025 scenario (8 tiers, 0.50/0.55/0.60 at top) → `scale = 0.11/0.11 = 1.0` → **28 of 32 profiles identical to baseline**.
- LFI-NFP-2025 scenario (14 tiers, 0.01→0.90) → `scale = 0.01/0.11 ≈ 0.09` → IR computed at ~9% of baseline for all profiles — the top 90% rate never activates.
- Renaissance-2025 scenario (4 tiers) → `scale = 0.11/0.11 = 1.0` → 4-tier simplification ignored, IR identical to baseline.

**Fix:**
```python
# In _compute_scenario_result, after extracting overrides at line 318:
# Replace the IR scale extraction and _compute_ir_bareme call with
# a function that actually uses the custom brackets:

def _compute_ir_bareme_custom(revenu_net: float, nb_parts: float, 
                               bareme_data: Dict) -> float:
    """Compute IR using custom bracket definitions."""
    brackets = bareme_data.get("brackets", [])
    if not brackets:
        # Fallback to baseline
        return _compute_ir_bareme(revenu_net, nb_parts, scale=1.0)
    
    qf = revenu_net / max(nb_parts, 0.5)
    ir_par_part = 0.0
    previous = 0.0
    
    for bracket in brackets:
        if not isinstance(bracket, dict):
            continue
        rate = bracket.get("rate", 0)
        threshold = bracket.get("threshold", float("inf"))
        if qf > previous:
            taxable = min(qf, threshold) - previous
            ir_par_part += taxable * rate
        previous = threshold
        if qf <= threshold:
            break
    
    return round(ir_par_part * nb_parts, 2)

# Then in _compute_scenario_result, replace lines 322-331 with:
ir_scale = 1.0
custom_bareme = None
if "impot_revenu.bareme" in overrides:
    bareme_data = overrides["impot_revenu.bareme"]
    if isinstance(bareme_data, dict) and "brackets" in bareme_data:
        custom_bareme = bareme_data

# And replace line 381 with:
if custom_bareme:
    ir = _compute_ir_bareme_custom(revenu_net_cat, nb_parts, custom_bareme)
else:
    ir = _compute_ir_bareme(revenu_net_cat, nb_parts, scale=ir_scale)
```

### CR-02: Type mismatch in `parameterOverrides` contract — Python produces `Record<string, any>`, TypeScript expects `Record<string, number>`

**Files:**
- `webapp/src/engine/types.ts:76` (declares `parameterOverrides: Record<string, number>`)
- `packages/data-pipeline/src/scenarios/precompute.py:510-512` (produces nested objects like `{brackets: [...]}`)
- `packages/data-pipeline/dist/scenarios-v2025.1.json` (contains complex nested objects)

**Issue:** The TypeScript `ScenarioDefinition` interface declares `parameterOverrides` as `Record<string, number>`. But the Python pipeline emits values that are complex objects:
- `{"brackets": [{"rate": 0.0, "threshold": 0}, ...]}` — not a number
- `1.05` — a number
- `true` — a boolean (for `revenu_universel.remplace_aides`)

TypeScript consumers that iterate `parameterOverrides` expecting `number` values will encounter type errors at runtime, and any code doing `Object.values(def.parameterOverrides).some(v => typeof v !== 'number')` will fail.

**Fix:**
```typescript
// webapp/src/engine/types.ts line 76
// Change:
parameterOverrides: Record<string, number>;
// To:
parameterOverrides: Record<string, unknown>;
```
Or more precisely:
```typescript
parameterOverrides: Record<string, number | boolean | { brackets: Array<{ rate: number; threshold: number }> }>;
```

### CR-04: `revenu_universel.remplace_aides` is a boolean but TypeScript declares `parameterOverrides: Record<string, number>`

**Files:**
- `packages/data-pipeline/src/scenarios/scenario_definitions.py:399` (defines `True`)
- `webapp/src/engine/types.ts:76`
- `packages/data-pipeline/dist/scenarios-v2025.1.json` (contains `"remplace_aides": true`)

**Issue:** The `revenu_universel.remplace_aides` override value in the JSON output is `true` (boolean), not a number. If any TypeScript code casts/reads this as a number, it will get `1` in coercion, but this is fragile and violates the type contract. With `parameterOverrides: Record<string, number>`, TypeScript will catch this at compile time if strict mode is on, but the pre-computed JSON in `scenarios-v2025.1.json` will cause runtime failures if the consumer validates types.

**Fix:** Align Python and TypeScript — either:
- Convert boolean to `1.0`/`0.0` in Python: `bool_val = True; json_val = 1.0 if bool_val else 0.0`
- Or update the TS type to `Record<string, number | boolean>`.

**File:** `packages/data-pipeline/dist/scenarios-v2025.1.json` (PS-2025 results block, lines 2088-2345)

### WR-03: `_estimate_aides` sets `aide_scales["apl"] = 1.0` when `reval == 0.0` — semantically empty assignment

**File:** `packages/data-pipeline/src/scenarios/precompute.py:345-348`
**Issue:**
```python
if "prestations_sociales.apl.revalorisation" in overrides:
    reval = float(overrides["prestations_sociales.apl.revalorisation"])
    if reval == 0.0:
        aide_scales["apl"] = 1.0  # noop: same as default apl_scale
```
When `reval == 0.0`, `aide_scales["apl"]` is set to `1.0`. But `_estimate_aides` already defaults to `apl_scale=1.0` (line 199). The assignment is a no-op. This looks like a regression from a version where `0.0` meant "freeze" (no increase from baseline), but the current code treats it identically to `1.0`.

**Fix:** If `reval == 0.0` should freeze APL (no change, but not `scale=1.0` of a different baseline), ensure the distinction is correct, or remove the dead assignment and add a clarifying comment:
```python
if reval == 0.0:
    aide_scales["apl"] = 1.0  # APL frozen at baseline level
elif reval > 0:
    aide_scales["apl"] = reval
```

### WR-04: CI workflow version check for openfisca-france is a soft warning, not a hard gate

**File:** `.github/workflows/phase2-wasm.yml:237-239`
**Issue:** The OpenFisca version range check prints `::warning` but does not exit non-zero if the version is outside 159-199. A version far outside this range (e.g., <150 or ≥200) could indicate breaking API changes that silently corrupt the pre-computed data without CI detection.

```yaml
  exit 1
fi
```
Or accept the soft-warning design but document the rationale in a comment.

## Info

### IN-01: Parameter overrides shallow-copied with dict comprehension — nested objects not deeply cloned

**File:** `packages/data-pipeline/src/scenarios/precompute.py:510-512`
**Issue:** `parameterOverrides` is copied via `{k: v for k, v in scenario.parameter_overrides.items()}` which creates a new top-level dict but reuses the nested objects (e.g., the `brackets` list with dict entries). If any downstream code mutates these, it could corrupt the source `ScenarioDefinition`. Currently this is benign because the JSON is write-only, but it's a fragile pattern.

**Fix:** Use `copy.deepcopy()` for the export:
```python
from copy import deepcopy
"parameterOverrides": deepcopy(dict(scenario.parameter_overrides)),
```

### IN-02: Unused import — `Optional` in precompute.py is imported but never used as a type annotation

**File:** `packages/data-pipeline/src/scenarios/precompute.py:26`
**Issue:** `from typing import Any, Dict, List, Optional` — `Optional` is imported but never used in any type annotation. Static type checkers (mypy, pyright) will flag this.

**Fix:** Remove `Optional` from the import line.

### IN-03: `_compute_ir_bareme` hardcodes 2025 French tax brackets without referencing the tax-rules YAML directory

**File:** `packages/data-pipeline/src/scenarios/precompute.py:134-139`
**Issue:** The baseline bracket thresholds and rates are hardcoded inline rather than loaded from `packages/tax-rules/parameters/`. If tax brackets change (e.g., 2026 law), the precompute engine must be manually edited, introducing a risk of drift between the YAML definitions and the computation.

**Fix:** Load brackets from the tax-rules YAML at compute time, or at minimum add a CI gate that cross-validates the hardcoded brackets against the YAML definitions:
```python
# CI gate suggestion:
# Compare hardcoded brackets against tax-rules/parameters/impot_revenu/bareme/*.yaml
```

### IN-04: `parameterOverrides` schema allows arbitrary objects — no validation of override value types

**File:** `packages/data-pipeline/src/scenarios/schemas/scenarios.schema.json:23`
**Issue:** The schema defines `"parameterOverrides": { "type": "object" }` with no additional constraints. This means any value shape passes validation — `{"brackets": [...], "scale": "not-a-number"}` would pass. While the Python pipeline produces correct shapes today, there's no schema-enforced contract preventing malformed overrides from reaching consumers.

**Fix:** Add property-level schemas for known override keys:
```json
"parameterOverrides": {
  "type": "object",
  "properties": {
    "impot_revenu.bareme": { "$ref": "#/definitions/irBareme" },
    "tva.taux_normal": { "type": "number", "minimum": 0, "maximum": 1 },
    "cotisations.scale": { "type": "number", "minimum": 0 },
    "prestations_sociales.rsa.socle": { "type": "number" },
    "prestations_sociales.prime_activite.montant_base": { "type": "number" },
    "prestations_sociales.allocations_familiales.modulation": { "type": "number" },
    "prestations_sociales.apl.revalorisation": { "type": "number" },
    "revenu_universel.montant_mensuel": { "type": "number" },
    "revenu_universel.remplace_aides": { "type": "boolean" }
  },
  "additionalProperties": false
}
```
