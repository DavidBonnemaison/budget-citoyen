## Summary

This phase executes the Python scenario pre-compute pipeline end-to-end, expanding from 3 to 12 scenarios and producing the `scenarios-v2025.1.json` artifact that the TypeScript `ScenarioCache` consumes for O(1) citizen-mode lookups. The existing infrastructure (`scenario_definitions.py`, `precompute.py`) is functional and well-structured — the pipeline already loads 32 canonical profiles, applies scenario parameter overrides via simplified Python tax/benefit formulas, and exports JSON in the exact `ScenarioDoc` contract format. The TypeScript engines (`scenario-cache.ts`, `macro-interpolate.ts`) and their vitest test suites (13 + tests passing) are complete and integration-ready.

The primary work is additive: defining 9 new `ScenarioDefinition` instances (5 political programs, 3 pedagogical, 3 single-axis variants), formalizing JSON Schema validation (Draft 2020-12) for the output document, creating a TypeScript integration test that validates the produced JSON through `ScenarioCache.fromDocs()`, and ensuring the CI pipeline executes and gates correctly. The critical environment constraint is that openfisca-france 175.0.40 (latest, within `>=159,<200`) requires Python ≤ 3.13 — the local dev environment runs Python 3.14.5 which is incompatible. However, the CI uses Python 3.10 and works correctly; local development can use `uv run --python 3.10` or a Python 3.10-3.13 virtualenv.

**Primary recommendation:** Use uv to manage Python versions for local development. Install openfisca-france in a Python 3.10-3.13 environment. Follow the existing `ScenarioDefinition` pattern exactly for the 9 new scenarios. Add a `scenarios.schema.json` (JSON Schema Draft 2020-12) that validates the output document structure. Add a TypeScript integration test that loads the committed JSON through `ScenarioCache.fromDocs()`. Update the CI scenario-precompute job to expect 12 scenarios (not 3) and add the schema validation step.

### Pattern 1: ScenarioDefinition Dataclass (Existing — Preserved)
**What:** Each scenario is a `@dataclass` with `id`, `name`, `description`, `parameter_overrides` dict. The `build_reform()` method lazily constructs an openfisca-france `Reform` subclass. The `get_scenario_definitions()` factory returns the full list.

**When to use:** All 12 scenarios follow this pattern. Copy the existing 3 scenarios as templates.

**Example:**
```python
# Source: packages/data-pipeline/src/scenarios/scenario_definitions.py (lines 24-85)
@dataclass
class ScenarioDefinition:
    id: str
    name: str
    description: str
    parameter_overrides: Dict[str, Any] = field(default_factory=dict)

    def build_reform(self):
        from openfisca_core.reforms import Reform  # lazy import
        from openfisca_france import FranceTaxBenefitSystem

        overrides = dict(self.parameter_overrides)
        scenario_id = self.id

        class ScenarioReform(Reform):
            name = f"Scénario {scenario_id}"
            key = scenario_id
            def apply(self):
                for param_path, new_value in overrides.items():
                    self.modify_parameters(
                        parameter_name=param_path,
                        period="year:2025:2025",
                        new_value=new_value,
                    )
        return ScenarioReform(FranceTaxBenefitSystem)
```

### Pattern 2: Simplified Computation with Override Extraction (Existing — Preserved)
**What:** `_compute_scenario_result()` in `precompute.py` extracts scenario overrides into scale factors consumed by simplified formulas. No full openfisca-france simulation is run. The Reform API is used only for parameter definition (contract), not computation.

**Key override-to-formula mappings (current):**
| Override Key | Extracted As | Feeds Into |
|-------------|-------------|------------|
| `impot_revenu.bareme` | `ir_scale` (ratio of first non-zero bracket rate / 0.11) | `_compute_ir_bareme(scale=ir_scale)` |
| `prestations_sociales.rsa.socle` | `aide_scales["rsa"]` | `_estimate_aides()` |
| `prestations_sociales.prime_activite.montant_base` | `aide_scales["prime_activite"]` | `_estimate_aides()` |
| `prestations_sociales.allocations_familiales.modulation` | `aide_scales["allocations_familiales"]` | `_estimate_aides()` |
| `prestations_sociales.apl.revalorisation` | `aide_scales["apl"]` (0.0 = freeze, else keep) | `_estimate_aides()` |
| `tva.taux_normal` | `taux_tva` | `_estimate_tva(taux_tva=...)` |

### Pattern 3: JSON Key Stringification (Existing — Preserved)
**What:** Profile indices stored as string keys (`"0"`, `"1"`, ...) in JSON output because JSON cannot represent numeric keys. TypeScript `ScenarioCache.addScenario()` converts back via `Number(key)`.

**Location:** `precompute.py` line 473: `results[str(idx)] = result`

### Pattern 4: Parameter Override Keys for New Scenarios
**What:** The simplified formulas understand a fixed set of parameter paths. New scenarios MUST use only these recognized keys. Arbitrary openfisca-france paths that don't map to an override extraction in `_compute_scenario_result()` will be silently ignored.

**Recognized override keys:**
| Key | Type | Effect |
|-----|------|--------|
| `impot_revenu.bareme` | `{"brackets": [...]}` | IR scale factor extracted from bracket rate ratio |
| `tva.taux_normal` | `float` (0.0-1.0) | Standard VAT rate |
| `prestations_sociales.rsa.socle` | `float` (>0) | RSA multiplier |
| `prestations_sociales.prime_activite.montant_base` | `float` (>0) | Prime d'activité multiplier |
| `prestations_sociales.allocations_familiales.modulation` | `float` (>0) | Allocations familiales multiplier |
| `prestations_sociales.apl.revalorisation` | `float` (0.0 = freeze) | APL revalorisation |

**For new scenario types that need novel effects:**
- **Cotisations changes:** Currently no override key exists. `_estimate_cotisations()` hardcodes `0.22 * scale` and `0.097 * scale` with `scale=1.0`. To add cotisation overrides, either (a) add a new recognized key like `cotisations.scale` and extract it in `_compute_scenario_result()`, or (b) add the key to `parameter_overrides` and extend the extraction logic.
- **Dépenses publiques (spending):** This affects macro sliders, not micro pre-compute. No micro parameter override needed.
- **Revenu universel:** No direct openfisca-france equivalent. Model as a flat transfer: extend `_estimate_aides()` with a `revenu_universel_montant` override key.

### Anti-Patterns to Avoid
- **Using full openfisca-france entity/period simulation:** Would take hours (60s/profile × 32 profiles × 12 scenarios ≈ 6.4h). Simplified formulas run in seconds and are cross-validated.
- **Adding override keys without extraction logic:** Keys in `parameter_overrides` that don't have corresponding extraction in `_compute_scenario_result()` are silently ignored.
- **Integer profile index keys in JSON:** JSON spec requires string keys. Always use `str(idx)`.
- **Hardcoding scenario count to 3:** CI currently checks `>= 3`. Update to `>= 12`.
- **Modifying `scenario-cache.ts` or `types.ts`:** These are consumer contracts — changing them breaks Phase 3. Add new scenarios, don't change the format.

## Common Pitfalls

### Pitfall 1: Python Version Incompatibility
**What goes wrong:** openfisca-france 175.0.40 requires Python ≥3.9 and ≤3.13. The local dev environment runs Python 3.14.5, causing `ModuleNotFoundError` or compilation failures.
**Why it happens:** openfisca-france depends on numpy with compiled extensions; Python 3.14 ABI is not yet supported.
**How to avoid:** Use `uv venv --python 3.10` for local development. CI already uses Python 3.10 (configured in `phase2-wasm.yml`).
**Warning signs:** `ModuleNotFoundError: No module named 'openfisca_france'` even after pip install; numpy build errors.

### Pitfall 2: Silently Ignored Parameter Overrides
**What goes wrong:** Adding a key to `parameter_overrides` that has no corresponding extraction logic in `_compute_scenario_result()` — the override is stored in JSON (visible in metadata) but has zero computational effect.
**Why it happens:** `_compute_scenario_result()` extracts specific known keys (lines 320-353 in precompute.py). Unknown keys are not processed.
**How to avoid:** Every override key added to a `ScenarioDefinition` must have a corresponding extraction block in `_compute_scenario_result()`. Document new keys in RESEARCH.md Pattern 4 table.
**Warning signs:** Scenario results identical to baseline despite non-empty `parameterOverrides` in JSON output.

### Pitfall 3: CI Scenario Count Gate Failure
**What goes wrong:** CI job `scenario-precompute` (line 194 in `phase2-wasm.yml`) checks `SCENARIO_COUNT -lt 3`. If the pipeline fails silently (e.g., only 3 baseline scenarios actually compute), CI passes but Phase 3 receives incomplete data.
**Why it happens:** The count check was written for 3 scenarios. 12 is the new minimum.
**How to avoid:** Update the CI gate from `-lt 3` to `-lt 12`. Additionally verify file size is within expected range (~50-100KB compressed for 12×32 profiles).
**Warning signs:** CI passes but `scenarios-v2025.1.json` only contains 3 entries.

### Pitfall 4: String Key vs Number Key Confusion
**What goes wrong:** Profile indices stored as integers in JSON output, causing `ScenarioCache.addScenario()` to fail on `Number(undefined)` during lookup.
**Why it happens:** JSON spec does not allow integer keys in objects. Python `json.dump` raises if given non-string keys.
**How to avoid:** Always use `str(idx)` when writing results (existing code already does this — preserve it).
**Warning signs:** TypeScript integration test fails with `undefined` lookups; JSON parse errors.

### Pitfall 5: Pedagogical Scenario Parameter Mapping
**What goes wrong:** "Revenu universel" has no direct openfisca-france equivalent. Trying to force it into existing override keys produces semantically wrong results.
**Why it happens:** The simplified formula model was designed for parametric reforms (rate changes, threshold shifts), not structural reforms (new transfer types).
**How to avoid:** For pedagogical scenarios, extend `_compute_scenario_result()` and `_estimate_aides()` with new override keys and simple additive/substitutive logic. Example: `revenu_universel.montant_mensuel` → adds flat monthly transfer, subtracts RSA + prime d'activité. Document the creative mapping in scenario descriptions.

### Pitfall 6: openfisca-france Version Drift
**What goes wrong:** CI installs `openfisca-france>=159,<200` and gets a newer version than what was used for local development, potentially changing parameter tree structure.
**Why it happens:** openfisca-france is continuously deployed (multiple releases per week). Parameter paths can change between versions.
**How to avoid:** Record exact openfisca-france version in output metadata (already done in `precompute_scenarios()`). CI version gate already warns if version is outside expected range. Add a hard pin in CI if drift becomes problematic.
**Warning signs:** CI failure after openfisca-france update with `KeyError` on parameter paths.

## Open Questions (RESOLVED)

1. **Parameter override values for political programs** (RESOLVED)
   - What we know: Each program should reflect publicly stated 2027 fiscal platforms. LFI/NFP typically proposes 14-bracket IR with 90% top rate, Renaissance proposes flat tax simplifications, LR proposes spending cuts and deficit reduction, RN proposes VAT reduction on essentials, PS proposes CSG reform.
   - What's unclear: Exact bracket thresholds, rates, and spending multipliers for each program as of early 2026.
   - Recommendation: Research each party's fiscal platform from public sources (programme présidentiel 2027, Institut Montaigne analyses). Use best-effort parameter estimates with clear documentation that values are approximate representations of publicly stated positions.
   - Resolution: Planned in Plan 01 Task 2 — 5 political programs defined with specific bracket thresholds, rates, and benefit multipliers documented in scenario descriptions.

2. **Revenu universel pedagogical scenario implementation** (RESOLVED)
   - What we know: No direct openfisca-france equivalent. Would require a flat monthly transfer that replaces RSA + prime d'activité.
   - What's unclear: Whether to extend `_estimate_aides()` with new logic, or handle as a separate computation step.
   - Recommendation: Add two new recognized override keys (`revenu_universel.montant_mensuel` and `revenu_universel.remplace_aides`) and extend `_estimate_aides()` to compute RU as: `montant_mensuel * 12 - sum(existing_aides)` when `remplace_aides` is true. Document the creative mapping in the scenario description.
   - Resolution: Planned in Plan 01 Task 3 — two new override keys added (`revenu_universel.montant_mensuel`, `revenu_universel.remplace_aides`) with RU logic at caller level (not inside `_estimate_aides()`), subtracting RSA + prime d'activité when `remplace_aides` is true, floor at RU amount.

3. **Cotisations sociales override mechanism** (RESOLVED)
   - What we know: `_estimate_cotisations()` hardcodes `0.22 * scale` and `0.097 * scale` with `scale=1.0`. There's no override key for cotisations.
   - What's unclear: Whether political programs (LR, RN) that propose cotisation changes need this capability, or whether cotisation effects are adequately captured through macro sliders.
   - Recommendation: Add a `cotisations.scale` recognized override key in `_compute_scenario_result()` that feeds into `_estimate_cotisations(scale=...)`. Default 1.0 (baseline). Only add if at least 2 new scenarios need it.
   - Resolution: Planned in Plan 01 Task 3 — `cotisations.scale` added as recognized override key (default 1.0), wired through `_estimate_cotisations(salaire_total, scale=cotisation_scale)`. 6 new scenarios use it (renaissance, lr, rn, transition-ecologique, revenu-universel, equilibre-budgetaire).

4. **JSON Schema strictness level** (RESOLVED)
   - What we know: CONTEXT.md D-08 requires JSON Schema Draft 2020-12 validation. The schema should validate minimum structure (12 scenarios, required fields, value types).
   - What's unclear: Whether to validate value ranges (e.g., `revenuDisponible > 0`, specific IR bracket thresholds) or just types.
   - Recommendation: Validate types and required fields strictly. Validate value ranges loosely (≥0 for monetary values, IS must be 0.0). Don't validate specific expected values (those belong in integration tests).
   - Resolution: Planned in Plan 01 Task 1 — schema validates types strictly (number, string, integer), required fields at all levels, value constraints loosely (`minimum: 0` for monetary values, `const: 0.0` for IS, `const: "v2025.1"` for version, `minItems: 12`, `minProperties: 32`). No specific expected values validated.

5. **CI job dependency chain for schema validation** (RESOLVED)
   - What we know: Current CI has `typescript-tests` depending on `scenario-precompute`. Schema validation needs to fit in.
   - What's unclear: Whether to add a separate `schema-validation` job between `scenario-precompute` and `typescript-tests`, or fold it into `scenario-precompute`.
   - Recommendation: Add schema validation as a step within the `scenario-precompute` job (after JSON export, before the count check). This keeps the CI graph simple (7 jobs) and ensures schema failure blocks downstream TypeScript tests.
   - Resolution: Planned in Plan 03 Task 1 — schema validation added as a step within the `scenario-precompute` CI job after JSON export and before the count gate, keeping the CI graph at 7 jobs.
